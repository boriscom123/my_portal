# Портал видеоуроков — дизайн системы

Дата: 2026-09-01. Статус: согласован с заказчиком, готов к написанию плана работ.

## 1. Что это и зачем

Портал автора видеоуроков. Решает три задачи:

1. **Витрина.** Единая точка, где лежат все уроки и новости, со ссылками на все
   площадки, где урок опубликован. Зритель приходит сюда, а не ищет по площадкам.
2. **Обратная связь.** Реакции, отзывы, комментарии и борд идей для следующих
   роликов — плюс сведение в одно место того, что люди пишут на самих площадках.
3. **Автоматизация публикации.** Автор загружает исходник один раз; система делает
   субтитры, тексты, нарезки и разливает ролик по площадкам.

Автор один — это заказчик. Личный кабинет = админка на одного человека.
Остальные пользователи только потребляют контент и оставляют обратную связь.

## 2. Рамки

### Делаем

- Публичная витрина уроков и новостей с серверным рендером.
- Авторизация шестью способами, сведённая к одному аккаунту.
- Реакции, отзывы и комментарии с модерацией.
- Борд идей с голосованием и статусами.
- PWA с Web Push как основной клиент.
- Конвейер обработки: транскрипт, субтитры, тексты, главы, вертикальные нарезки.
- Публикация на площадки в трёх режимах (авто / полуавто / ручной).
- Сбор метрик и комментариев с площадок, где есть API.
- Мини-приложения Telegram и MAX.

### Не делаем

- **Не храним видеоархив.** Портал видео не раздаёт: зритель смотрит через
  встроенный плеер площадки. Файлы живут в рабочем буфере на время обработки
  и публикации, затем удаляются по сроку.
- **Не делаем свой плеер и транскодинг.**
- **Не делаем мультиавторство.** Автор один; чужие OAuth-токены не храним.
- **Не импортируем архив** — проект стартует с нуля, роликов пока нет.

### Отложено сознательно

| Что | Когда вернуться |
|---|---|
| Календарь и отложенная публикация | После этапа 8: пока площадка одна, откладывать нечего |
| Курсы и плейлисты | Когда наберётся ~10 уроков; на трёх это мёртвая функция |
| Премодерация комментариев моделью | В день первого спама, не раньше |
| E-mail дайджест | Вероятно никогда: телеграм-канал дешевле и его читают |
| Google Play и App Store | Когда появится аудитория (решение заказчика) |

## 3. Ограничения среды

Боевой VPS: **2 ядра, 3.8 ГБ памяти (около 2 ГБ уже занято, swap заполнен),
27 ГБ свободного диска, GPU нет.** На машине уже работает десяток чужих контейнеров.

Из этого следуют три жёстких решения, а не пожелания:

1. **Расшифровка речи — только внешним сервисом.** Локальный Whisper на двух ядрах
   без GPU идёт примерно со скоростью реального времени и на час работы выводит из
   строя остальные сервисы машины.
2. **Тяжёлая работа с видео — в отдельном контейнере, строго по одной задаче за раз,
   с пониженным приоритетом.** ffmpeg в одном процессе с веб-сервером сделает портал
   неотзывчивым на всё время нарезки.
3. **Никакого постоянного видеоархива на диске.** 27 ГБ хватает на рабочий буфер
   в два-три ролика, но не на библиотеку. Внешнее S3-хранилище не нужно именно
   потому, что архива нет.

## 4. Архитектура

### Контейнеры

В компоузе портала три сервиса:

| Сервис | Что делает |
|---|---|
| `api` | Express. JSON API для всех клиентов + серверный рендер публичных страниц |
| `worker` | Node с ffmpeg. Разбирает очередь: расшифровка, нарезка, публикация, сбор метрик |
| `db` | PostgreSQL 16, свой том, своя база |

Переиспользуется существующая инфраструктура, новых сервисов не появляется:

- **Redis** — уже поднятый `claudeservice-redis-1` через сеть `claude-net`,
  со своим префиксом ключей. Там только очередь задач; потеря не катастрофична,
  поэтому второй Redis не нужен.
- **nginx** — уже работающий контейнер проекта game (`game_world_tycoon_idle-nginx-1`).
  Дописываем конфиг сайта, как это сделано для uzbek_queue и myproject. TLS оттуда же.

Собственный Postgres, а не база проекта game: перезапуск чужого компоуза не должен
ронять портал.

### Стек

Набор инструментов тот же, что во всех существующих Node-проектах на этом VPS, —
чтобы эксплуатация не менялась: **Node, Express, `pg`, `redis`, `passport`
(Google-стратегия уже написана в проекте game и берётся оттуда), `jsonwebtoken`.**
Очередь — **BullMQ** поверх Redis: даёт повторы, задержки и расписание из коробки.

Версии при этом берутся текущие, а не те, что стоят в старых проектах: репозиторий
публичный и показательный. Конкретные версии и практики — в разделе 11.

Фронт — **серверный рендер HTML шаблонами плюс немного ванильного JS**. React и Next.js
сознательно отвергнуты: витрине уроков они не нужны, а по памяти на этой машине они
дороже всего остального портала вместе взятого.

### Клиенты

Ядро системы — **API, а не сайт**. Сайт — один из клиентов. Клиентов четыре, все
ходят в один и тот же API на одном origin:

1. **PWA** — основной канал взаимодействия, ради него всё.
2. **Веб-сайт** — витрина для поисковиков и для пришедших по ссылке.
3. **Мини-приложение Telegram** — отдельная страница, опознающая пользователя
   по данным мессенджера.
4. **Мини-приложение MAX** — то же самое.

Вся пользовательская логика идёт через JSON API. Серверные HTML-страницы существуют
только ради индексации и разворачивания превью ссылок; логики в шаблонах нет.

### Адрес

Стартуем на `nip.io`-адресе, как остальные проекты. **Адрес нигде не хардкодится** —
живёт одной переменной окружения, из которой собираются все ссылки, redirect URI
и манифест PWA.

Известный риск, принятый заказчиком: установленная PWA и подписки Web Push привязаны
к origin. Смена IP сервера обрывает и то и другое у всех пользователей разом,
переустанавливать придётся вручную каждому. Точка невозврата — день, когда приложение
впервые уйдёт людям; к этому дню домен должен быть куплен.

## 5. Модель данных

PostgreSQL. Ничего экзотического, поиск — встроенный полнотекстовый с русским словарём.

### Пользователи

- **`users`** — человек: отображаемое имя, аватар, роль, дата регистрации.
- **`identities`** — способы входа: провайдер, идентификатор у провайдера, ссылка на
  `users`. Уникальность по паре (провайдер, идентификатор). Шесть провайдеров:
  `tg_widget`, `tg_miniapp`, `max_miniapp`, `google`, `vk`, `yandex`.

Разделение обязательно с первого дня: без него один и тот же человек, зашедший
с сайта и из мини-приложения, превратится в два аккаунта с разной историей.

### Контент

- **`lessons`** — урок: slug, заголовок, описание, обложка, состояние, дата выхода,
  длительность.
- **`news`** — новость: slug, заголовок, текст, дата.
- **`tags`**, **`lesson_tags`** — теги.
- **`publications`** — по строке на каждую площадку каждого урока: площадка, внешний
  идентификатор, ссылка, состояние, режим публикации, текст ошибки. Отсюда карточка
  урока собирает кнопки «смотреть на».
- **`transcripts`** — цельный текст расшифровки урока.
- **`transcript_segments`** — отрезки с таймкодами: начало, конец, текст. Дают поиск
  по словам внутри урока с переходом на нужную секунду.
- **`assets`** — файлы: вид (исходник, нарезка, субтитры, обложка), путь, **срок
  жизни**. По сроку буфер чистит себя сам.

### Обратная связь

- **`reactions`** — реакция пользователя на объект; одна на пару (пользователь, объект).
- **`comments`** — комментарий: автор, объект, родитель для веток, текст, состояние
  модерации.
- **`ideas`** — идея следующего ролика: автор, тема, описание, статус
  (`new` / `accepted` / `in_progress` / `released`), ссылка на вышедший урок.
- **`idea_votes`** — голос за идею; один на пару (пользователь, идея).

### Уведомления

- **`push_subscriptions`** — подписки Web Push.
- **`notifications`** — журнал отправленного: кому, о чём, каким каналом. Нужен,
  чтобы одно событие не улетело человеку трижды по трём каналам.

### Внешний мир

- **`platform_accounts`** — токены доступа к площадкам. Одна строка на площадку,
  так как автор один. Токены шифруются ключом из окружения.
- **`metrics`** — снимки просмотров, лайков и числа комментариев по публикации.
- **`external_comments`** — стянутые с площадок комментарии, привязанные к публикации.
- **`short_links`**, **`link_hits`** — свои короткие ссылки с метками и их клики,
  для сквозной аналитики независимо от API площадок.

## 6. Авторизация и роли

Шесть способов входа, но механик всего три:

1. **Обычный OAuth 2.0** — Google, VK, Яндекс. Устроены одинаково, различаются
   адресами и названиями полей. Пишется один раз, настраивается трижды.
2. **Виджет Telegram на сайте** — не OAuth. Телеграм отдаёт данные пользователя
   с подписью; сервер пересчитывает HMAC по токену бота и сверяет.
3. **Вход внутри мини-приложения** (Telegram и MAX) — приложение получает от
   мессенджера подписанные данные о том, кто его открыл. Проверка похожа на пункт 2.

Все шесть путей сходятся в одну процедуру:

- привязка найдена → входим под её пользователем;
- привязка не найдена, но пользователь уже авторизован → привязываем к нему;
- иначе → заводим нового пользователя.

**Сессия.** Один токен в одном формате, два способа доставки: защищённая от чтения
скриптами кука для сайта и PWA; тот же токен заголовком для мини-приложений, где
куки ненадёжны.

**Роли три:**

| Роль | Может |
|---|---|
| Гость | Только читать |
| Пользователь | Реакции, отзывы, комментарии, идеи, голоса |
| Админ (заказчик) | Уроки, публикации, модерация, подключения к площадкам |

## 7. Уведомления

Отдельный слой с несколькими каналами. Вызывающий код **не знает, куда шлёт**:
он говорит «уведомить такого-то о таком-то», слой выбирает канал по тому, что у
человека есть, в порядке приоритета:

1. активная подписка Web Push → пуш в приложение;
2. иначе есть привязка Telegram → сообщение ботом;
3. иначе есть привязка MAX → сообщение его ботом;
4. иначе молчим.

Один человек получает **одно** уведомление, а не три. Отправленное пишется в журнал,
чтобы повтор задачи не задвоил сообщение.

Поводы уведомить пользователя: вышел новый урок; ответили на его комментарий;
идея, за которую он голосовал, сменила статус или по ней вышел урок.
Поводы уведомить админа: публикация на площадку упала; пришёл комментарий на модерацию.

Web Push уже реализован и работает в проекте myproject; ключи VAPID и логика подписки
переносятся оттуда без переделки.

## 8. Путь урока от файла до отзывов

Шесть состояний. **Каждый шаг конвейера — отдельная задача в очереди, результат
которой сразу ложится в базу.** Это принципиально: упавшая на середине расшифровка
при повторе доделывается с места обрыва, а не начинается заново. На двух ядрах
иначе неприемлемо.

1. **Черновик.** Автор завёл карточку и загрузил исходник. Дальше можно закрыть телефон.
2. **Обработка.** Очередь по порядку: извлечь звук → внешняя расшифровка → транскрипт
   с таймкодами → субтитры → модель даёт три варианта заголовка, описание, теги и
   главы с таймкодами → нарезка вертикальных фрагментов со вшитыми субтитрами →
   кадр на обложку.
3. **Проверка** — обязательный ручной шаг. Автор открывает урок в приложении и видит
   готовое: выбирает заголовок из трёх, правит описание, отмечает годные нарезки и
   целевые площадки. **Наружу ничего не уходит, пока он не нажал.** Без этого шага
   автопубликации не будет доверия.
4. **Публикация.** По строке на площадку, каждая живёт своей жизнью и падает
   независимо. Упавшее повторяется с нарастающей паузой; окончательно упавшее
   показывается в кабинете красным, а не прячется.
5. **Опубликован.** Карточка на портале ожила: описание, обложка, кнопки «смотреть на»
   по каждой площадке, транскрипт попал в поиск. Уходит анонс в телеграм-канал и пуш
   подписчикам.
6. **Жизнь после выхода.** Воркер по расписанию обходит площадки с API, тянет
   просмотры, лайки и новые комментарии. Файлы в буфере доживают срок и удаляются;
   карточка урока остаётся.

## 9. Адаптеры площадок

Публикация на площадку скрыта за адаптером с единым интерфейсом. У адаптера
**три режима зрелости**, и это следствие того, что полноценный автопостинг возможен
не везде:

| Режим | Что делает |
|---|---|
| `auto` | Загружает и публикует сам |
| `semi` | Готовит черновик на площадке и шлёт автору уведомление «зайди и дожми» |
| `manual` | Отдаёт архив с видео, обложкой, субтитрами и текстами плюс чек-лист |

Реальное положение дел на момент проектирования:

| Площадка | Режим | Ограничение |
|---|---|---|
| YouTube | `auto` | Квота: около 6 загрузок в сутки по умолчанию, расширение по заявке |
| VK Video | `auto` | — |
| Telegram | `auto` | Бот отдаёт до 50 МБ; снимается своим Bot API сервером |
| RuTube | `auto` | Нужен доступ от площадки |
| TikTok | `semi` | Публикация только после ревью приложения; иначе ролик уходит в черновики |
| Instagram | `semi` | Только Business/Creator аккаунт через Graph API; с личного нельзя |
| Dzen | `manual` | Публичного API загрузки нет |
| MAX | `manual` | API ботов есть; публикация видео в ленту требует отдельной проверки |

Трёхрежимный адаптер существует именно затем, чтобы добавление площадки не ломало
систему и чтобы `manual`-площадки всё равно получали готовые материалы.

## 10. Обратная связь и аналитика

**Консолидация.** В кабинете одна сводная страница на урок: сверху цифры по каждой
площадке и суммарно, ниже — все комментарии единой лентой с пометкой источника,
вперемешку с отзывами с самого портала.

**Что реально доступно.** Комментарии по API есть у YouTube и VK. У TikTok и Instagram —
только по своим постам и через Business API. У Dzen, RuTube и MAX практически никак.
Реалистичная цель: метрики там, где есть API, плюс собственные реакции и отзывы портала.

**Свои короткие ссылки.** Ссылки на площадки идут через редирект портала с метками
источника. Это даёт честную сквозную статистику «откуда пришёл зритель» независимо
от того, отдаёт площадка API или нет.

**Борд идей** живёт своей жизнью: люди предлагают тему, голосуют, автор меняет статус.
Когда урок по идее вышел, идея закрывается ссылкой на него, а всем голосовавшим
уходит уведомление. Самый дешёвый в реализации кусок и лучший способ вернуть человека.

## 11. Соглашения по коду и репозиторию

Репозиторий публичный и служит учебным материалом: по нему снимаются уроки
о разработке. Поэтому требования к нему выше обычных — он должен быть понятен
человеку, который открыл его впервые и не знает ни проекта, ни автора.

### Комментарии

**Обязательное требование заказчика.** Блочный комментарий над объявлением,
отвечающий на три вопроса:

1. какую задачу выполняет;
2. зачем нужен;
3. где используется — кто его вызывает.

Обязателен **всегда** для: файла (модуля), класса, функции, сервиса.
Обязателен для переменных и констант там, где имя не объясняет себя само,
а также для всех настроек, порогов и любых чисел с неочевидным смыслом.

Пункт 3 обязателен наравне с остальными: он заменяет читателю поиск по
репозиторию. Комментарии на русском. Пересказ сигнатуры комментарием не считается.

Сознательное исключение: комментарий вида «счётчик циклов» над счётчиком циклов
не пишем. Шум обесценивает те комментарии, которые несут смысл, и в учебном
репозитории это вреднее, чем их отсутствие.

### Версии и практики

Требование заказчика — свежие версии и современные практики, потому что
репозиторий показательный. При этом набор инструментов остаётся тем же, что уже
работает на сервере: Node, Express, PostgreSQL, Redis. Меняются версии и способ
их применения, а не состав.

| Что | Решение | Почему |
|---|---|---|
| Node | 24 LTS | Текущий LTS; всё ниже показывать в уроках 2026 года незачем |
| Express | 5 | Корректная обработка ошибок в асинхронных обработчиках |
| Модули | ESM | Современный стандарт; CommonJS в новом коде не заводим |
| Тесты | встроенный `node:test` | Минус тяжёлая зависимость из публичного репозитория |
| Стиль | ESLint 9 (flat config) + Prettier | Код в кадре всегда выглядит одинаково |
| CI | GitHub Actions на каждый коммит: линт, тесты, сборка образа | В открытом репозитории зелёная сборка — это доверие |
| Образ | многоступенчатая сборка, запуск не от root | Базовая гигиена, которую видно в Dockerfile |
| Зависимости | автообновление | Репозиторий не должен протухать между уроками |
| Коммиты | единый формат сообщений | Их видно в кадре чаще, чем код |

### История разработки

В репозитории рядом с кодом лежит переписка с заказчиком: `docs/history/<дата>.md`.
Смысл — дать зрителю урока воспроизвести путь своими словами: видно, какой фразой
попросили и что из этого вышло.

**Что попадает.** Только текст, прошедший через Telegram-бота: сообщения заказчика
и ответы, отправленные ему. Вывод команд не попадает **физически** — он через эти
точки не проходит. Что именно менялось в коде, смотрится по коммитам за ту же дату;
дублировать это текстом незачем.

**Как пишется.** Запись врезана в мост Telegram в проекте ClaudeService:
`scripts/history-log.sh`, вызываемый из `watch-triggers.sh` (входящие),
`tg-send.sh` и `tg-ask.sh` (исходящие). По умолчанию выключена во всех проектах;
включается наличием файла `docs/history/.enabled` в конкретном проекте — чтобы
переписка по закрытым проектам никуда не попала.

**Что вычищается.** Поверх этого — автозамена домашних путей, IP-адресов и всего,
похожего на токен или ключ, на понятные заглушки. Диалог — это проза, секретов там
почти не бывает, но адрес сервера проскакивает регулярно.

### Прочее

Файлы держим небольшими и с одной ответственностью; миграции базы —
версионированные файлы, применяются при старте.

### Секреты и конфигурация

**Репозиторий публичный.** Ни один секрет не попадает в код и в git.

- Всё чувствительное живёт в `.env` рядом с компоузом; `.env` закрыт `.gitignore`.
- В репозитории лежит `.env.example` — полный список переменных с пустыми
  значениями и пояснением, зачем каждая нужна. Новая переменная добавляется
  в образец тем же коммитом, что и код, который её читает.
- Список закрытого: пароль базы, ключ подписи сессий, ключ шифрования токенов
  площадок, пара ключей Web Push, токены ботов Telegram и MAX, реквизиты
  приложений всех OAuth-провайдеров и площадок, ключ облака для расшифровки.
- **Адрес портала тоже в `.env`** — он содержит IP сервера. Это же правило уже
  действует в проекте game, где по той же причине из репозитория убраны привязки
  портов.
- Долгоживущие токены доступа к площадкам хранятся в базе **в зашифрованном виде**,
  ключом из окружения. В `.env` лежат только реквизиты приложений.
- Рабочий буфер с исходниками и нарезками закрыт `.gitignore` наравне с секретами:
  чужое видео в публичном репозитории — такая же утечка.

## 12. План реализации

Одиннадцать этапов. Каждый заканчивается не отчётом, а действием, которое заказчик
делает руками и видит результат. Проверка не прошла — дальше не идём.

| Этап | Содержание | Критерий приёмки |
|---|---|---|
| 0 | Каркас: компоуз из трёх контейнеров, миграции, маршрут в nginx, сертификат, заглушка | Адрес открывается по https; после перезагрузки VPS всё поднялось само |
| 1 | Вход: Google и виджет Telegram, таблица привязок, роли, токен | Вошёл Google, вышел, вошёл Telegram — **один** аккаунт; гость отзыв отправить не может |
| 2 | Витрина: уроки, новости, карточка, лента, теги, реакции, отзывы с модерацией | Урок виден из инкогнито; реакция засчитана; неодобренный комментарий гостю не виден |
| 3 | PWA и уведомления: манифест, service worker, офлайн, иконки, Web Push, слой каналов, телеграм-бот | Поставил с домашнего экрана, опубликовал урок с ноутбука — пуш пришёл. Проверка на Android **и** на iPhone отдельно |
| 4 | Борд идей: предложить, проголосовать, статусы, уведомления голосовавшим | С телефона предложил, со второго аккаунта проголосовал, сменил статус — уведомление пришло |
| 5 | Конвейер, текст: загрузка, очередь, расшифровка, транскрипт, субтитры, тексты от модели, экран проверки, поиск | Залил настоящий урок — через минуты есть субтитры и три заголовка; поиск слова из середины урока ведёт на нужную секунду |
| 6 | Конвейер, видео: нарезки, вшитые субтитры, обложка, автоудаление буфера | Из часового урока вышли смотрибельные шортсы; по сроку файлы исчезли, карточка цела |
| 7 | Публикация на YouTube: подключение, очередь, повторы, состояния, показ ошибок | Нажал «опубликовать» — ролик на канале с верными заголовком, описанием, тегами, главами и субтитрами; ссылка встала в карточку |
| 8 | Остальные площадки по одной: VK, телеграм-канал, RuTube, затем TikTok и Instagram в режиме `semi`, затем Dzen и MAX в `manual` | Площадка не считается сделанной, пока настоящий ролик туда не уехал |
| 9 | Обратная связь: сбор метрик и комментариев, сводная страница, короткие ссылки со счётчиком | Через сутки после выхода в кабинете живые цифры и живые комментарии с двух площадок в одной ленте |
| 10 | Мини-приложения Telegram и MAX | Открыл в мессенджере — узнало без логина, показало ленту, реакция засчиталась в тот же аккаунт, что и на сайте |

После этапа 4 у заказчика уже полноценный живой портал с приложением на телефоне.
Всё, что дальше, — автоматизация.

**Как пишутся планы работ.** Одиннадцать этапов — слишком много для одного плана,
он получится нечитаемым и устареет к середине. Подробный план работ пишется
порциями: сначала на этапы 0–4 (портал и приложение), затем, после их сдачи, —
на этапы 5–6 (конвейер), затем на 7–8 (публикация), затем на 9–10. Каждая порция
опирается на то, что уже сдано и проверено, а не на предположения.

## 13. Открытый вопрос

**Чем расшифровывать речь и генерировать тексты.** По умолчанию закладывается
**Яндекс SpeechKit** для расшифровки и **YandexGPT** для заголовков и описаний:
сервер российский, оплата рублями со счёта без сложностей с зарубежными картами,
качество на русской речи хорошее, порядок цен — рубли за урок.

Обращение к сервису идёт через тонкий слой, поэтому замена на другой поставщик —
правка одного файла, а не переделка конвейера. Окончательное решение принимается
**на этапе 5**, после прогона настоящего урока и оценки результата глазами.
