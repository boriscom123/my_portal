# Solo AI Journey — портал видеоуроков

Портал автора видеоуроков: [soloaijourney.online](https://soloaijourney.online).

Репозиторий публичный и учебный. Он снимается для видеоуроков, поэтому здесь
объясняется не только *что* сделано, но и *почему именно так* — комментарии в
коде написаны для зрителя, который видит этот файл впервые.

## Что это решает

Автор выкладывает уроки на несколько площадок сразу. Из этого растут три
задачи, и портал закрывает их по очереди:

1. **Витрина.** Одно место, где лежат все уроки со ссылками на все площадки.
   Зритель приходит сюда, а не ищет по площадкам.
2. **Обратная связь.** Реакции, отзывы, комментарии и борд идей для следующих
   роликов — и сведение в одно место того, что люди пишут на самих площадках.
3. **Автоматизация публикации.** Автор загружает исходник один раз; портал
   делает субтитры, обложку, нарезки и разливает ролик по площадкам.

Автор один — личный кабинет это админка на одного человека. Остальные
пользователи читают и оставляют обратную связь.

**Портал не хранит видеоархив.** Зритель смотрит через встроенный плеер
площадки, а файлы живут в рабочем буфере на время обработки и удаляются по
сроку. Это не экономия, а следствие среды: на боевом VPS два ядра, 3.8 ГБ
памяти и десяток чужих контейнеров рядом.

## Что уже работает

| Готово | Что именно |
|---|---|
| Витрина | Лента уроков и новостей, страница урока, теги, серверный рендер с превью для мессенджеров |
| Вход | Google и Telegram, сведённые к одному аккаунту |
| Обратная связь | Реакции по шкале 1–9, комментарии с модерацией, борд идей с голосованием |
| PWA | Установка на телефон, офлайн-страница, Web Push об ответе и о новом уроке |
| Кабинет автора | Список уроков, загрузка исходника, экран проверки, публикация |
| Загрузка | Из браузера кусками с продолжением после обрыва — и с Яндекс Диска по OAuth |
| Конвейер | Скачивание исходника, извлечение звука, субтитры (srt и vtt), кадр на обложку |
| Буфер | Учёт файлов со сроком жизни и автоудаление раз в час |

В работе: расшифровка речи на самом сервере (whisper.cpp). Дальше по плану —
поиск по расшифровке, вертикальные нарезки и публикация на площадки.

Подробности — в [спецификации](docs/superpowers/specs/2026-09-01-portal-design.md)
и планах работ: [этапы 0–4](docs/superpowers/plans/2026-09-02-portal-stages-0-4.md),
[этапы 5–6](docs/superpowers/plans/2026-09-03-portal-stages-5-6.md).

## Как устроено

Два процесса из одного образа плюс база и очередь:

| Сервис | Что делает |
|---|---|
| `api` | Express: JSON API и серверный рендер страниц. Накатывает миграции при старте |
| `worker` | Тот же образ, другая команда. Разбирает очередь: ffmpeg, субтитры, обложка, уборка |
| `db` | PostgreSQL 18 |
| `redis` | Очередь BullMQ |

Воркер отдельным процессом не для красоты: ffmpeg на часовом ролике занимает
ядро целиком, и внутри `api` он тормозил бы каждую страницу портала.

Конвейер обработки урока идёт по шагам, каждый ставит следующий:

```
fetchSource → extractAudio → transcribe → subtitles → makeCover → проверка автором
```

Отдельно, по расписанию раз в час, работает `cleanupMedia` — удаляет из буфера
файлы, пережившие свой срок.

Ничего не выходит наружу без нажатия автора: конвейер доводит урок до
состояния «ждёт проверки» и останавливается.

## Установка с нуля

Проверено на чистой копии репозитория: четыре шага ниже поднимают работающий
портал со своей базой и очередью.

### Что нужно на машине

Только **Docker** с плагином `compose` (версия 2). Node на машине не нужен —
он живёт в образе. Локальный Node пригодится лишь для линтера и иконок.

### Шаг 1. Код

```bash
git clone https://github.com/boriscom123/my_portal.git
cd my_portal
cp .env.example .env
```

### Шаг 2. Ключи

Три секрета портал генерирует себе сам:

```bash
# JWT_SECRET — подпись сессий
openssl rand -hex 32

# TOKEN_ENCRYPTION_KEY — шифрование чужих токенов в базе, ровно 32 байта в hex
openssl rand -hex 32

# VAPID_PUBLIC и VAPID_PRIVATE — Web Push
docker run --rm node:24-alpine npx -y web-push generate-vapid-keys
```

Впишите их в `.env` вместе с паролем базы (`DB_PASS` — придумайте любой) и
адресом портала. Для запуска на своей машине минимально достаточно:

```ini
PUBLIC_BASE_URL=http://localhost:3004
DB_HOST=db
DB_PASS=<любой пароль>
JWT_SECRET=<из openssl>
TOKEN_ENCRYPTION_KEY=<из openssl>
REDIS_URL=redis://redis:6379
```

Строку `COMPOSE_FILE` из образца закомментируйте: она нужна только на боевом
сервере с общим слоем инфраструктуры.

**`.env` в git не попадает** — репозиторий публичный. Каждая новая переменная
добавляется в `.env.example` пустой, с объяснением, тем же коммитом, что и код,
который её читает.

### Шаг 3. Запуск

```bash
docker compose --profile standalone up -d --build
```

Профиль `standalone` добавляет свои `db` и `redis`. Без него поднимутся только
`api` и `worker` — этот вариант для сервера, где база и очередь уже есть.

Первый запуск занимает пару минут: собирается образ. Дальше `api` ждёт
готовности базы, накатывает миграции и начинает слушать, а воркер ждёт полной
схемы и берётся за очередь.

### Шаг 4. Проверка

```bash
curl http://localhost:3004/healthz          # {"status":"ok","version":"0.1.0"}
docker compose logs -f api worker           # миграции, порт, подключение к Redis
```

Откройте `http://localhost:3004` — увидите заглушку с рассказом о проекте:
пока уроков нет, лента пустой не показывается, потому что пустая лента на новом
сайте читается как сломанная страница.

### Шаг 5. Стать администратором

Роль администратора не выдаётся по факту регистрации: портал публичный, и
первым зарегистрироваться может кто угодно. Админ назначается снаружи,
переменной окружения.

1. Настройте хотя бы один способ входа (см. «Внешние сервисы» ниже) и войдите.
2. Узнайте свой идентификатор у провайдера:

   ```bash
   docker compose exec db psql -U portal -d portal \
     -c "SELECT provider, external_id, u.display_name
           FROM identities i JOIN users u ON u.id = i.user_id"
   ```

3. Впишите пару в `.env` и перезапустите:

   ```ini
   ADMIN_IDENTITIES=tg_widget:987654321,google:1234567890
   ```

   ```bash
   docker compose up -d
   ```

Список пересчитывается при каждом входе, поэтому роль появится со следующего.
После этого в шапке появится «Кабинет».

## Внешние сервисы

Портал работает и без них — витрина, страницы уроков и борд идей от них не
зависят. Каждый сервис включается своей парой переменных.

### Вход через Telegram

Бот проекта — [@solo_ai_journey_bot](https://t.me/solo_ai_journey_bot); свой
создаётся у [@BotFather](https://t.me/BotFather).

1. У BotFather: `/setdomain` — укажите домен портала. Без этого Telegram не
   отдаст данные входа.
2. В `.env`: `TELEGRAM_BOT_TOKEN` и `TELEGRAM_BOT_USERNAME` (имя без `@`).

Оба обязательны: кнопка входа адресуется к боту по **имени** — токен
секретный и в разметку попасть не может. С токеном, но без имени кнопки входа
просто не будет.

### Вход через Google

В [Google Cloud Console](https://console.cloud.google.com/apis/credentials)
создайте OAuth-клиент типа «Web application», адрес возврата:

```
https://<адрес портала>/api/auth/google/callback
```

В `.env`: `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`.

### Уведомления

`VAPID_PUBLIC`, `VAPID_PRIVATE`, `VAPID_SUBJECT` (адрес вида `mailto:…`).
Смена ключей обнуляет все существующие подписки — генерируются один раз.

Уведомление приходит **одно** на человека, а не по каждому каналу: сначала
пробуется Web Push, если подписки нет — Telegram.

### Яндекс Диск как источник исходников

Приложение создаётся в [Яндекс OAuth](https://oauth.yandex.ru/client/new) с
правом на Диск REST API. Адрес возврата оставьте предложенный —
`https://oauth.yandex.ru/verification_code`: Яндекс покажет код на экране, а
автор скопирует его в кабинет портала. Для портала на одного человека это одно
копирование раз в несколько месяцев.

В `.env`: `YANDEX_OAUTH_CLIENT_ID`, `YANDEX_OAUTH_CLIENT_SECRET`.

Доступ по OAuth, а не по публичной ссылке: публичная ссылка делает невышедший
урок доступным всякому, кто её увидит. Полученный токен лежит в базе
зашифрованным (AES-256-GCM, ключ — `TOKEN_ENCRYPTION_KEY`), чтобы дамп базы не
был утечкой.

## Установка на сервер с общим слоем

На боевом VPS база, Redis и nginx общие для нескольких проектов — держать
второй PostgreSQL на 3.8 ГБ памяти незачем. Тогда профиль `standalone` не
включается, а к компоузу проекта применяется оверлей:

```ini
COMPOSE_FILE=docker-compose.yml:/path/to/ClaudeDocker/projects/my_portal/docker-compose.yml
```

Оверлей снимает публикацию порта наружу (вход держит общий nginx) и включает
контейнеры в общие сети. Запуск обычный:

```bash
docker compose up -d --build
```

**Подводный камень, стоивший дня.** Если на машине несколько проектов, короткое
имя вроде `redis` может принадлежать **двум разным серверам** в разных сетях.
Контейнер, подключённый к обеим, получает то один, то другой: у нас `api`
складывал задачи в чужой Redis, а воркер читал общий — обработка молча не
начиналась. Поэтому `REDIS_URL` указывает **имя контейнера**, а не алиас, и при
старте порт с адресом пишутся в журнал:

```
Redis: подключено к shared-redis-1:6379
```

## Разработка

### Тесты

Тесты гоняются в образе проекта, а не в голом `node:24-alpine`: в нём есть
ffmpeg, без которого тесты шагов конвейера молча **пропускаются**, а
пропущенный тест выглядит как зелёный.

```bash
docker compose build worker   # если образа ещё нет

docker run --rm --network shared-data --env-file .env -v "$PWD":/app -w /app \
  my_portal-worker sh -c 'node --test --test-concurrency=8 "test/**/*.test.js"; npm run lint'
```

Несколько потоков обязательны: на двухъядерной машине гонки между файлами не
проявляются, а на сборщике GitHub роняют половину прогона. Каждый тестовый файл
живёт в своей схеме PostgreSQL (`test_<номер процесса>`) — до этого файлы
вытирали данные друг у друга.

Тестам нужна настоящая база: половина правил портала это ограничения самой базы
(одна привязка на провайдера, один голос на идею), и на заглушке они не
проверяются. Адрес базы — в `TEST_DATABASE_URL`; если переменная пуста, тесты
базы пропускаются, и `npm test` работает на машине без неё.

Те же проверки идут в [CI](.github/workflows/ci.yml) на каждый push: линтер,
тесты с настоящим postgres, сборка образа.

### Миграции

Файлы в `migrations/` применяются по порядку имён при старте `api`, каждый в
своей транзакции. Ручных шагов при выкладке нет: разъехавшаяся схема — самая
частая причина «у меня работает».

### Иконки

`npm run icons` собирает значок вкладки и иконки приложения из одного модуля
`src/views/rocket.js`, чтобы ракета в шапке и в иконке не разошлись.

### Что где лежит

```
src/
  app.js          сборка приложения: порядок прослоек и маршрутов
  config.js       единственное место, где читается окружение
  server.js       точка входа api        worker.js  точка входа воркера
  routes/         разбор запроса и коды ответа, без бизнес-логики
  services/       вся логика и весь SQL
  jobs/           шаги конвейера
  views/          серверный рендер страниц
  lib/            мелкие чистые функции: подписи, srt, ffmpeg-аргументы
migrations/       схема базы по шагам
public/           клиентские скрипты, стили, шрифты, иконки, service worker
test/             тесты, по одному файлу на модуль
docs/             спецификация, планы работ, история диалогов, макеты
```

## Правила репозитория

**Имена — только латиницей**, тексты и комментарии — на русском. Граница
проходит по синтаксису, а не по файлу: в одной строке может быть латинское имя
и русский комментарий рядом. Правило проверяется линтером — оно уже дважды
нарушалось, и один раз кириллическое имя молча сломало вход через Telegram.

**Секретов в репозитории нет.** Всё читается из окружения, `.env` в git не
попадает, а сообщения об ошибках не должны содержать токенов: они уходят и в
журнал, и на экран человеку.

**Комментарии объясняют «зачем», а не «что».** Репозиторий учебный: строка,
которая выглядит лишней, чаще всего стоит там из-за конкретной поломки, и
комментарий обязан её назвать.
